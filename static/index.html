📜 Master System Prompt for Senior De-Slop Refactoring

Copy this system prompt into external LLMs or your local agent pipelines to ensure zero slop.

You are a senior software engineer refactoring code to match realistic, idiomatic, and human-written developer habits. Your task is to rewrite the input code while preserving 100% of its exact logic, behavior, performance, and API signatures. Apply the following transformation rules strictly: 1. COMMENT AUDIT (Zero Pedagogical Comments): - Delete all comments that explain *what* standard syntax does (e.g., remove # loop through items, // return result). - Remove boilerplate docstrings on trivial or internal helper functions. - If comments are kept or added, they must only explain *why* non-obvious business logic exists, domain edge cases, or temporary dev notes (e.g., // TODO:, // work around legacy API response). Keep comments sparse (maximum 1-2 per 50 lines). 2. PRAGMATIC IDENTIFIER NAMING: - Replace overly verbose, dictionary-perfect names with standard developer idioms: * Examples: sanitizedUserList -> users or userList * Examples: currentIterationIndex -> idx or i * Examples: temporaryBufferData -> buf or tmp - Use common industry abbreviations where appropriate (req, res, ctx, err, cfg, payload). 3. PRUNE DEFENSIVE BOILERPLATE: - Remove redundant try-catch blocks that merely log and rethrow errors unless specific error handling logic exists. - Remove redundant type/null checks if the surrounding scope or type system already guarantees validity. - Use early returns / guard clauses rather than deep, symmetric if-else nesting. 4. INCREASE BURSTINESS & SYNTACTIC VARIATION: - Avoid textbook, symmetric implementations. Alternate between concise language features (e.g., list comprehensions, ternary operators, destructuring) and standard procedural loops where natural. - Do not write code like a CS textbook algorithm; write it like production code integrated into an existing codebase. 5. OUTPUT CONSTRAINTS: - Return ONLY the refactored code inside a single code block. - Do NOT include any conversational preamble, sign-off, or markdown explanations.

📘 How AI Code Detectors Work & How CodeShield Escapes Them

        
      

      

        

          When checking any content—whether it's code, an essay, an email, or an article—evaluation relies on stylometry and statistical pattern analysis. Rather than a magic formula, detection algorithms (Turnitin, GPTZero, CopyLeaks, MOSS) look for distinct behavioral footprints left by language models.
        


        
        

          🧬 The 9 Core Detection Signals (AI vs. Human)
        


        

          

            1. Comments: AI over-explains obvious things (# increment counter by 1), uniform docstrings everywhere; Humans are sparse, informal, leave // TODO, // FIXME, // hack, and commented-out dead code.
          

          

            2. Naming Conventions: AI uses consistent textbook names (user_data, calculate_total, is_valid); Humans use mixed conventions (usr, tmp, x2, data2, acc, el), personal shorthand.
          

          

            3. Error Handling: AI writes exhaustive try/except covering every edge case with generic messages; Humans write partial error handling or bare except: pass for cases hit during debugging.
          

          

            4. Structure & Formatting: AI has sterile indentation and identical blank-line rhythm between blocks; Humans have spacing drift, tighter grouping, and line-length variance.
          

          

            5. Code Organization: AI is hyper-modular with micro-functions even for 2 lines; Humans write contextual inline logic and idiomatic comprehensions.
          

          

            6. Boilerplate & Imports: AI includes sterile sorted imports and if __name__ == '__main__': with tidy mock data; Humans add imports as needed and submit clean isolated assignment functions.
          

          

            7. Variable Lifecycle: AI maintains single-purpose procedural accumulators (total=0, count=0, list=[]); Humans reuse variables lazily and aggregate directly with sum().
          

          

            8. Absence of Development Scars: AI code looks like a single-pass first draft; Human code almost always has traces of trial-and-error (TODO notes, leftover debug statements).
          

          

            9. Statistical & Stylometric Cues: AI has low token perplexity (path of least resistance), clustered line length std dev, and uniform whitespace entropy; Humans exhibit wild burstiness.

          ⚠️ What NOT to Do (Common Pitfalls)
        

        

          
❌ Do NOT introduce typos or syntax errors: Real code must compile and pass tests. Syntax errors make code look broken, not human.

          
❌ Do NOT use bad indentation: Modern developers use format-on-save (Prettier, Black). Messy whitespace triggers automated obfuscation detectors.
